# **13. include 관계 (\<\<include\>\>)**
---
## **1) include 관계의 개념**
include 관계는
**한 유스케이스가 다른 유스케이스를 반드시 포함하여 수행하는 관계**이다.
즉,
A 유스케이스가 실행될 때
항상 B 유스케이스가 함께 수행된다.
---
## **2) include 관계의 목적**
- 공통 기능을 분리
- 기능 재사용
- 중복 제거
- 모델 단순화
---
## **3) 표현 방법**
- 점선 화살표 사용
- \<\> 표기
- 기본 유스케이스 → 포함 유스케이스 방향
형식:
기본 유스케이스 ──\<\>──▶ 포함 유스케이스
---
## **4) include 관계의 특징**
- 항상 실행된다.
- 조건이 없다.
- 포함되는 기능은 독립 유스케이스이다.
- 여러 유스케이스에서 재사용 가능하다.
---
## **5) 예시 1: 로그인 검증**
유스케이스:
- 주문 생성
- 회원 정보 수정
- 게시글 작성
이 모든 기능은
"로그인 확인"이 필요하다고 가정한다.
따라서,
주문 생성 ──\<\>──▶ 로그인 확인
회원 정보 수정 ──\<\>──▶ 로그인 확인
게시글 작성 ──\<\>──▶ 로그인 확인
로그인 확인은 공통 기능이 된다.
---
## **6) 예시 2: 결제 시스템**
유스케이스:
- 주문 생성
주문 생성은 항상 결제 요청을 포함한다면
주문 생성 ──\<\>──▶ 결제 요청
---
## **7) include 사용 기준**
다음 질문에 "예"이면 include 고려
- 여러 유스케이스에서 공통으로 사용되는 기능인가?
- 항상 수행되는 기능인가?
- 분리했을 때 재사용성이 높아지는가?
---
## **8) 잘못된 사용 예**
### **1. 조건이 있는 경우**
조건부 기능은 include가 아니다.
→ extend 관계 사용
### **2. 내부 처리 로직 포함**
DB 저장, 데이터 검증 등
내부 로직은 include 대상이 아니다.
---
## **9) include vs 일반 호출의 차이**
include는 모델링 관점에서
공통 기능을 구조적으로 분리한 것이다.
단순 내부 함수 호출과는 다르다.
---
## **10) 시험 핵심 포인트**
- include는 항상 수행
- 공통 기능 분리 목적
- 점선 화살표 + \<\>
- 방향은 기본 → 포함 대상
---
## **핵심 정리**
- include = 항상 포함되는 공통 기능
- 재사용 목적
- 점선 화살표 사용
- 조건이 있으면 extend 사용

# **14. extend 관계 (\<\<extend\>\>)**
---
## **1) extend 관계의 개념**
extend 관계는
**기본 유스케이스의 기능을 조건적으로 확장하는 관계**이다.
즉,
A 유스케이스가 수행되는 도중
특정 조건이 만족될 때 B 유스케이스가 추가로 수행된다.
---
## **2) extend 관계의 목적**
- 선택적 기능 추가
- 예외 처리 모델링
- 조건부 흐름 표현
- 기본 기능과 확장 기능 분리
---
## **3) 표현 방법**
- 점선 화살표 사용
- \<\> 표기
- 확장 유스케이스 → 기본 유스케이스 방향
형식:
확장 유스케이스 ──\<\>──▶ 기본 유스케이스
※ include와 방향이 반대임에 주의
---
## **4) extend 관계의 특징**
- 조건이 있다.
- 선택적으로 실행된다.
- 기본 유스케이스는 독립적으로 실행 가능하다.
- 확장 유스케이스는 단독 실행이 어렵다.
---
## **5) 예시 1: 할인 쿠폰 적용**
기본 유스케이스:
- 주문 생성
확장 유스케이스:
- 할인 쿠폰 적용
조건:
- 사용자가 쿠폰을 보유한 경우
구조:
할인 쿠폰 적용 ──\<\>──▶ 주문 생성
---
## **6) 예시 2: 비밀번호 오류 처리**
기본 유스케이스:
- 로그인
확장 유스케이스:
- 비밀번호 재입력
조건:
- 비밀번호가 일치하지 않는 경우
---

<td>조건부 실행</td>
</tr>

<td>기능 확장</td>

## **8) extend 사용 기준**
다음 질문에 "예"이면 extend 고려
- 기능이 선택적인가?
- 특정 조건에서만 실행되는가?
- 기본 기능 없이 단독 수행이 어려운가?
---
## **9) 잘못된 사용 예**
1. 항상 실행되는 기능을 extend로 표현 → X
2. 공통 기능을 extend로 표현 → X
3. 내부 처리 로직을 extend로 표현 → X
---
## **10) 시험 핵심 포인트**
- extend는 조건부 실행
- 점선 화살표 사용
- 방향은 확장 → 기본
- 기본 유스케이스는 독립 실행 가능
---
## **핵심 정리**
- extend = 조건적 확장 기능
- 선택적으로 실행됨
- include와 방향이 반대
- 공통 기능이 아니라 확장 기능임

# **15. include vs extend 비교 정리**
---
## **1) 기본 개념 차이**
### **include 관계**
- 한 유스케이스가 다른 유스케이스를 **항상 포함하여 수행**
- 공통 기능 분리 목적
- 재사용 중심 구조
---
### **extend 관계**
- 기본 유스케이스의 기능을 **조건적으로 확장**
- 선택적 기능 표현
- 예외/옵션 흐름 모델링
---

## **7) 판단 기준 질문**
### **include인지 판단하는 질문**
- 여러 유스케이스에서 공통으로 사용되는가?
- 항상 수행되는가?
- 기능 재사용이 목적인가?
YES → include
---
### **extend인지 판단하는 질문**
- 조건이 존재하는가?
- 선택적으로 수행되는가?
- 기본 기능은 독립적으로 완전한가?
YES → extend
---
## **8) 시험에서 자주 나오는 함정**
1. "조건이 있는 기능"을 include로 표현 → 오답
2. "항상 수행되는 공통 기능"을 extend로 표현 → 오답
3. 화살표 방향 반대로 그림 → 오답
---
## **9) 한 줄 요약**
- include = 항상 포함되는 공통 기능
- extend = 조건부 확장 기능
- 방향이 서로 반대
---
## **핵심 정리**
include는 재사용 중심, 항상 실행
extend는 확장 중심, 조건부 실행
화살표 방향이 시험 핵심 포인트이다.

# **16. 일반화(Generalization) 관계**
---
## **1) 일반화(Generalization)의 개념**
일반화 관계란
**상위 요소의 특성을 하위 요소가 상속받는 관계**를 의미한다.
즉,
공통적인 특성을 상위 개념으로 추상화하고
하위 개념이 이를 물려받는 구조이다.
객체지향의 상속 개념과 유사하다.
---
## **2) 표현 방법**
- 실선 + 빈 삼각형 화살표
- 하위 요소 → 상위 요소 방향
형식:
하위 ─────▷ 상위
---
## **3) 일반화 적용 대상**
일반화 관계는 다음 두 대상에 적용 가능하다.
1. 액터(Actor) 간
2. 유스케이스(Use Case) 간
---
## **4) 액터 일반화**
### **개념**
여러 액터가 공통 특성을 가질 경우
상위 액터로 묶는다.
---
### **예시**
상위 액터:
- 사용자
하위 액터:
- 일반 회원
- 관리자
구조:
일반 회원 ─────▷ 사용자
관리자 ─────▷ 사용자
의미: 일반 회원과 관리자는
사용자의 모든 기능을 상속받는다.
---
## **5) 유스케이스 일반화**
### **개념**
공통 기능을 가지는 여러 유스케이스를
상위 유스케이스로 추상화한다.
---
### **예시**
상위 유스케이스:
- 결제
하위 유스케이스:
- 카드 결제
- 계좌 이체
- 간편 결제
구조:
카드 결제 ─────▷ 결제
계좌 이체 ─────▷ 결제
간편 결제 ─────▷ 결제
의미: 각 결제 방식은
공통 결제 기능을 기반으로 확장된 형태이다.
---
## **6) 일반화 vs include / extend 차이**

</tr>
<tr>
<td>목적</td>
<td>상속 구조 표현</td>
<td>공통 기능 포함</td>
<td>조건부 확장</td>
</tr>

<td>실행 관계</td>
<td>상속 개념</td>
<td>항상 실행</td>

## **7) 일반화 사용 기준**
다음 조건을 만족하면 사용한다.
- 공통 기능을 추상화할 수 있는가?
- 역할 계층 구조가 존재하는가?
- 여러 유형을 상위 개념으로 묶을 수 있는가?
---
## **8) 자주 발생하는 오류**
1. 단순 포함 관계를 일반화로 표현 → X
2. 조건부 기능을 일반화로 표현 → X
3. 관계 방향을 잘못 그림 → X
---
## **9) 시험 핵심 포인트**
- 일반화는 상속 개념
- 실선 + 빈 삼각형 화살표
- 하위 → 상위 방향
- 액터와 유스케이스 모두 적용 가능
---
## **핵심 정리**
- 일반화는 계층 구조 표현
- 객체지향 상속과 유사
- include / extend와 목적이 다름
- 방향과 기호 구분이 중요
