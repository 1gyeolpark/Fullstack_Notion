# **1. 요구사항 분석의 개념**
---
## **1) 요구사항(Requirement)이란?**
요구사항이란 **사용자 또는 이해관계자가 시스템에 기대하는 기능과 제약 조건을 명확히 정의한 것**을 의미한다.
즉,
- 시스템이 무엇을 해야 하는가?
- 어떤 조건을 만족해야 하는가?
- 어떤 환경에서 동작해야 하는가?
에 대한 구체적인 정의이다.
---
## **2) 요구사항 분석(Requirement Analysis)이란?**
요구사항 분석은 이해관계자로부터 요구사항을 수집하고,
이를 정제·구조화·문서화하여 개발 가능한 형태로 만드는 과정이다.
단순히 요구를 듣는 것이 아니라,
1. 모호한 표현을 제거하고
2. 중복을 제거하며
3. 충돌을 해결하고
4. 구현 가능한 수준으로 구체화하는 과정이다.
---
## **3) 요구사항 분석의 목적**
- 시스템의 범위를 명확히 한다.
- 개발자와 사용자 간의 오해를 방지한다.
- 추후 설계 및 구현의 기준을 마련한다.
- 프로젝트 실패 위험을 줄인다.
요구사항 분석이 부정확하면
설계·구현·테스트 전 단계가 모두 흔들리게 된다.
---
## **4) 요구사항 분석의 중요성**
소프트웨어 프로젝트 실패의 주요 원인 중 하나는
'잘못된 요구사항 정의'이다.
요구사항이 명확하지 않으면:
- 개발 방향이 달라진다.
- 추가 비용이 발생한다.
- 일정이 지연된다.
- 품질 문제가 발생한다.
따라서 요구사항 분석은 소프트웨어 개발 생명주기(SDLC)에서
가장 중요한 초기 단계이다.
---
## **5) 요구사항 분석의 주요 활동**
1. 요구사항 도출(Elicitation)
	- 인터뷰
	- 설문
	- 회의
	- 브레인스토밍
2. 요구사항 분석(Analysis)
	- 중복 제거
	- 충돌 해결
	- 우선순위 결정
3. 요구사항 명세(Specification)
	- 문서화
	- 모델링(UML, 유스케이스 등)
4. 요구사항 검증(Validation)
	- 이해관계자 확인
	- 테스트 가능성 점검
---
## **6) 요구사항 분석의 산출물**
- 요구사항 명세서(SRS)
- 유스케이스 다이어그램
- 유스케이스 명세서
- 기능 목록(Function List)
- 요구사항 추적표(Traceability Matrix)
---
## **7) 요구사항과 유스케이스의 관계**
유스케이스는 **기능 요구사항을 시나리오 형태로 구조화한 모델**이다.
즉,
요구사항 → 기능 단위 분리 → 유스케이스로 표현
이라는 흐름으로 연결된다.
---
## **핵심 정리**
- 요구사항은 시스템이 해야 할 일과 제약을 정의한 것
- 요구사항 분석은 이를 구체화·정제하는 과정
- 프로젝트 성공의 핵심 단계
- 유스케이스는 요구사항을 모델링하는 도구

# **2. 기능 요구사항 / 비기능 요구사항**
---
## **1) 기능 요구사항 (Functional Requirement)**
기능 요구사항은
시스템이 반드시 수행해야 하는 기능을 정의한 요구사항이다.
즉,
- 시스템이 무엇을 해야 하는가?
- 사용자가 어떤 작업을 수행할 수 있어야 하는가?
를 명확히 기술한 것이다.
---
### **특징**
- 동작 중심의 요구사항
- 사용자의 행위와 직접적으로 연결됨
- 유스케이스로 표현 가능
- 테스트 가능해야 함
---
### **작성 예시**
- 사용자는 회원 가입을 할 수 있다.
- 사용자는 상품을 검색할 수 있다.
- 관리자는 회원을 삭제할 수 있다.
- 시스템은 로그인 요청을 인증해야 한다.
---
### **표현 방식**
일반적으로 다음과 같은 형식을 사용한다.
- "\~할 수 있다"
- "\~해야 한다"
- "\~을 수행한다"
---
## **2) 비기능 요구사항 (Non-Functional Requirement)**
비기능 요구사항은
시스템의 품질 속성 또는 제약 조건을 정의한 요구사항이다.
즉,
- 얼마나 빠르게?
- 얼마나 안전하게?
- 얼마나 안정적으로?
- 어떤 환경에서?
와 같은 품질 기준을 명시한다.
---
### **특징**
- 시스템의 성능, 보안, 안정성 등과 관련
- 직접적인 기능이 아님
- 측정 가능해야 함
- 시스템 전체에 영향을 줌
---
### **주요 유형**
1. 성능(Performance)
2. 보안(Security)
3. 신뢰성(Reliability)
4. 사용성(Usability)
5. 확장성(Scalability)
6. 유지보수성(Maintainability)
7. 이식성(Portability)
---
### **작성 예시**
- 시스템은 1초 이내에 검색 결과를 반환해야 한다.
- 시스템은 하루 10,000명 동시 접속을 지원해야 한다.
- 비밀번호는 암호화하여 저장해야 한다.
- 시스템 가동률은 99% 이상이어야 한다.
---
## **3) 기능 요구사항 vs 비기능 요구사항 비교**

## **4) 시험 및 실무에서 자주 나오는 포인트**
- 유스케이스는 기능 요구사항을 모델링한다.
- 비기능 요구사항은 다이어그램으로 표현하기 어렵다.
- 비기능 요구사항은 반드시 수치화하는 것이 좋다.
- 모호한 표현은 제거해야 한다.
	- "빠르게 처리한다" → X
	- "2초 이내 처리한다" → O
---
## **핵심 정리**
- 기능 요구사항 = 시스템이 하는 일
- 비기능 요구사항 = 시스템의 품질 기준
- 유스케이스는 기능 요구사항 중심으로 작성한다.
- 비기능 요구사항은 측정 가능하게 기술해야 한다.

# **3. 유스케이스의 정의와 목적**
---
## **1) 유스케이스(Use Case)의 정의**
유스케이스란
**사용자가 시스템을 통해 특정 목표를 달성하는 과정을 시나리오 형태로 표현한 모델**이다.
즉,
- 누가(Actor)
- 무엇을 하기 위해
- 시스템과 어떻게 상호작용하는가
를 구조적으로 나타낸 것이다.
유스케이스는 기능 요구사항을 사용자 중심 관점에서 표현하는 방법이다.
---
## **2) 유스케이스의 핵심 구성 요소**
1. Actor(액터)
	- 시스템 외부에서 상호작용하는 주체
	- 사람, 외부 시스템, 장치 등
2. Use Case(유스케이스)
	- 사용자가 시스템을 통해 수행하는 기능 단위
3. System Boundary(시스템 경계)
	- 모델링 대상 시스템의 범위
---
## **3) 유스케이스의 목적**
### **1. 사용자 관점의 기능 정의**
기술 중심이 아니라
사용자 중심으로 기능을 정의한다.
### **2. 요구사항을 구조화**
모호한 요구사항을 기능 단위로 분리한다.
### **3. 개발 범위 명확화**
시스템이 해야 할 일과
하지 말아야 할 일을 구분한다.
### **4. 의사소통 도구 제공**
개발자, 기획자, 고객 간 공통 이해 기반을 마련한다.
---
## **4) 유스케이스의 특징**
- 기능 요구사항 중심
- 사용자 목표 중심
- 시나리오 기반 표현
- 테스트 케이스 도출에 활용 가능
---
## **5) 유스케이스 예시**
요구사항 문장:
"사용자는 로그인할 수 있다."
유스케이스 표현:
- 액터: 사용자
- 유스케이스: 로그인
- 기본 흐름:
	1. 아이디 입력
	2. 비밀번호 입력
	3. 로그인 버튼 클릭
	4. 인증 성공 시 메인 화면 이동
이처럼 단순 문장을
행위 중심의 시나리오로 확장하는 것이 유스케이스이다.
---
## **6) 유스케이스와 요구사항의 관계**
요구사항 → 기능 단위 분리 → 유스케이스 모델링 → 설계/구현
즉, 유스케이스는
요구사항을 설계 단계로 연결하는 중간 다리 역할을 한다.
---
## **7) 실무/시험 핵심 포인트**
- 유스케이스는 내부 처리 로직을 설명하지 않는다.
- 사용자와 시스템 간 상호작용만 표현한다.
- 하나의 유스케이스는 하나의 사용자 목표를 가진다.
- 이름은 "동사 + 목적어" 형태로 작성한다.
예:
- 회원 가입
- 상품 조회
- 주문 등록
---
## **핵심 정리**
- 유스케이스는 사용자 중심 기능 모델
- 기능 요구사항을 구조화한 표현 방법
- 시스템과 외부 주체 간 상호작용을 나타냄
- 설계 및 테스트의 기준이 됨

# **4. 유스케이스 기반 모델링의 필요성**
---
## **1) 왜 유스케이스로 모델링하는가?**
요구사항은 대부분 자연어로 표현된다.
예:
- 사용자는 상품을 검색할 수 있다.
- 관리자는 회원을 관리해야 한다.
자연어는 모호하고 해석 차이가 발생하기 쉽다.
유스케이스는 이러한 모호성을 줄이기 위해
기능을 구조적으로 정리하는 모델링 기법이다.
---
## **2) 문제점: 자연어 요구사항의 한계**
1. 모호성
	- "빠르게 처리한다"
	- "편리하게 사용한다"
2. 중복
	- 동일 기능이 다른 표현으로 여러 번 등장
3. 누락
	- 예외 상황이 고려되지 않음
4. 충돌
	- 서로 다른 이해관계자의 요구가 상충
---
## **3) 유스케이스 기반 모델링의 효과**
### **1. 기능 단위 분리**
시스템을 사용자 목표 중심으로 분해한다.
예:
- 로그인
- 상품 조회
- 주문 생성
- 결제 처리
---
### **2. 시스템 범위 명확화**
시스템 경계를 설정함으로써
- 시스템이 해야 할 기능
- 시스템 외부 기능
을 명확히 구분할 수 있다.
---
### **3. 사용자 중심 설계 가능**
내부 구현이 아닌
사용자의 행위 중심으로 시스템을 설계한다.
이는 UX 및 기능 흐름 설계에 직접 연결된다.
---
### **4. 테스트 기준 제공**
각 유스케이스는
하나의 테스트 시나리오가 된다.
즉,
유스케이스 → 테스트 케이스 도출 가능
---
### **5. 의사소통 도구**
- 기획자
- 개발자
- 고객
간의 공통 이해 기반을 형성한다.
다이어그램은 텍스트보다 이해가 빠르다.
---
## **4) 실무에서의 활용 흐름**
요구사항 수집
→ 기능 단위 정리
→ 유스케이스 다이어그램 작성
→ 유스케이스 명세서 작성
→ 설계/구현
→ 테스트 케이스 작성
---
## **5) 유스케이스 모델링이 필요한 상황**
- 기능이 많은 시스템
- 이해관계자가 많은 프로젝트
- 요구사항 변경 가능성이 높은 프로젝트
- 문서화가 중요한 공공/대규모 프로젝트
---
## **6) 시험 핵심 포인트**
- 유스케이스는 기능 요구사항 모델링 도구이다.
- 사용자 목표 중심 모델이다.
- 시스템 경계를 명확히 하기 위해 사용한다.
- 설계 및 테스트의 기준이 된다.
---
## **핵심 정리**
- 자연어 요구사항의 한계를 보완하기 위해 필요하다.
- 기능을 사용자 목표 단위로 구조화한다.
- 시스템 범위를 명확히 한다.
- 개발과 테스트의 기준을 제공한다.
