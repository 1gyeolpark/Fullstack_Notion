# **5. 시스템(System)과 시스템 경계(System Boundary)**

---

## **1) 시스템(System)의 개념**

시스템이란

**특정 목적을 달성하기 위해 구성 요소들이 상호작용하는 집합체**이다.

유스케이스 모델링에서의 시스템은

"우리가 개발하려는 대상 소프트웨어"를 의미한다.

즉,

- 웹 애플리케이션

- 모바일 앱

- ATM 시스템

- 도서 관리 시스템

등이 모델링 대상 시스템이 된다.

---

## **2) 시스템 경계(System Boundary)란?**

시스템 경계란

**모델링 대상 시스템의 범위를 구분하는 경계선**이다.

- 시스템 내부 기능

- 시스템 외부 요소(액터)

를 구분하기 위해 사용한다.

유스케이스 다이어그램에서는

사각형으로 표현한다.

---

## **3) 시스템 경계의 역할**

### **1. 개발 범위 정의**

- 시스템이 담당하는 기능

- 외부 시스템이 담당하는 기능

을 명확히 구분한다.

---

### **2. 책임 구분**

예:

결제 시스템을 예로 들면,

- 우리 시스템: 주문 요청

- 외부 PG 시스템: 실제 결제 처리

이처럼 책임을 명확히 구분해야 한다.

---

### **3. 과도한 모델링 방지**

시스템 외부 기능까지 포함하면

모델이 복잡해지고 혼란이 발생한다.

경계 설정은 모델 단순화를 돕는다.

---

## **4) 시스템 내부 vs 외부 구분 기준**

### **내부(Inside)**

- 우리가 개발하는 기능

- 제어 가능한 기능

- 구현 대상 기능

### **외부(Outside)**

- 사용자

- 외부 API

- 외부 서버

- 외부 장치

---

## **5) 예시: 온라인 쇼핑몰**

### **시스템 내부**

- 회원 가입

- 로그인

- 상품 검색

- 주문 생성

### **시스템 외부**

- 사용자

- 결제 대행 시스템

- 배송 업체 시스템

---

## **6) 시스템 경계 설정 시 주의사항**

1. 프로젝트 범위를 먼저 정의한다.

2. 외부 시스템과의 인터페이스를 고려한다.

3. 너무 넓거나 너무 좁게 설정하지 않는다.

4. 요구사항과 일치하는 범위로 설정한다.

---

## **7) 시험 핵심 포인트**

- 시스템 경계는 사각형으로 표현한다.

- 액터는 시스템 외부에 위치한다.

- 유스케이스는 시스템 경계 내부에 위치한다.

- 경계 설정은 개발 범위 정의와 직결된다.

---

## **핵심 정리**

- 시스템은 개발 대상 소프트웨어

- 시스템 경계는 개발 범위를 나타냄

- 내부와 외부를 명확히 구분하는 것이 중요

- 유스케이스 다이어그램의 기본 구조 요소

---

# **6. 액터(Actor)의 정의 및 유형**

---

## **1) 액터(Actor)의 정의**

액터란

**시스템 외부에서 시스템과 상호작용하는 주체**를 의미한다.

즉,

- 시스템을 사용하는 사람

- 시스템과 연동되는 외부 시스템

- 장치(Device)

등이 액터가 될 수 있다.

중요한 점은

액터는 시스템 내부 구성 요소가 아니라는 것이다.

---

## **2) 액터의 특징**

- 시스템 외부에 존재한다.

- 시스템과 데이터를 주고받는다.

- 하나 이상의 유스케이스와 연결된다.

- 역할(Role) 개념이다 (개인 이름이 아니다).

예:

- "김철수" → X

- "회원" → O

---

## **3) 액터의 유형**

### **1. 주 액터(Primary Actor)**

- 시스템을 사용하는 주체

- 목표 달성을 위해 시스템을 사용

- 유스케이스를 시작하는 주체

예:

- 사용자

- 관리자

- 고객

---

### **2. 보조 액터(Secondary Actor)**

- 시스템을 지원하는 외부 요소

- 시스템의 요청에 응답하는 역할

예:

- 결제 시스템

- 외부 인증 서버

- SMS 발송 서버

---

## **4) 사람만 액터인가?**

아니다.

다음도 모두 액터가 될 수 있다.

- 외부 API 서버

- 결제 대행 시스템

- 다른 소프트웨어

- 하드웨어 장치

기준은 "시스템 외부에 존재하는가?"이다.

---

## **5) 액터 식별 방법**

요구사항 문장에서 다음 표현을 찾는다.

- "사용자는 …"

- "관리자는 …"

- "시스템은 외부 결제 시스템과 …"

행위의 주체를 찾으면 액터를 도출할 수 있다.

---

## **6) 액터 일반화(Generalization)**

액터 간에도 상속 관계가 존재할 수 있다.

예:

- 사용자 ├─ 일반 회원 └─ 관리자

상위 액터의 유스케이스를

하위 액터가 상속받는다.

---

## **7) 자주 발생하는 오류**

1. 내부 모듈을 액터로 정의

	- DB 서버 → X (내부라면 액터 아님)

2. 개인 이름 사용

	- 홍길동 → X

3. 시스템 자체를 액터로 표현

	- 시스템은 액터가 아니다.

---

## **8) 시험 핵심 포인트**

- 액터는 시스템 외부 주체

- 사람, 시스템, 장치 모두 가능

- 역할 단위로 정의

- 유스케이스 시작 주체는 주 액터

---

## **핵심 정리**

- 액터는 시스템 외부의 역할

- 사람뿐 아니라 외부 시스템도 가능

- 역할 중심으로 정의해야 함

- 유스케이스와 연결되는 주체

---

# **7. 유스케이스(Use Case)의 정의 및 식별 기준**

---

## **1) 유스케이스의 정의 (재정리)**

유스케이스란

**액터가 시스템을 이용하여 특정 목표를 달성하는 기능 단위**이다.

중요한 점은

"하나의 사용자 목표"를 중심으로 정의한다는 것이다.

---

## **2) 유스케이스의 특징**

- 사용자 관점에서 작성

- 기능 요구사항 중심

- 하나의 목표를 가짐

- 동사 + 목적어 형태로 명명

예:

- 회원 가입

- 로그인

- 주문 생성

- 상품 검색

---

## **3) 유스케이스 식별 기준**

### **1. 사용자 목표 중심인가?**

다음 질문을 던진다.

"사용자가 이 기능을 통해 달성하려는 목표는 무엇인가?"

목표가 명확하지 않으면 유스케이스가 아니다.

---

### **2. 독립적으로 의미가 있는가?**

- 단독으로 실행 가능한 기능인가?

- 하나의 완료 상태를 가지는가?

예:

- 비밀번호 입력 → X (단독 목표 아님)

- 로그인 → O (하나의 완료 목표)

---

### **3. 외부 액터와 상호작용이 있는가?**

내부 처리 로직만 존재한다면

유스케이스로 보기 어렵다.

유스케이스는 반드시

"액터 ↔ 시스템" 간 상호작용이 있어야 한다.

---

## **4) 유스케이스 식별 절차**

1. 요구사항 문장 수집

2. 행위 동사 추출

3. 목표 단위로 묶기

4. 중복 제거

5. 적절한 수준으로 조정

## **7) 유스케이스의 적정 분해 수준**

### **너무 세분화하면**

- 다이어그램이 복잡해짐

- 관리 어려움

### **너무 포괄적이면**

- 흐름이 길어짐

- 테스트 불명확

적절한 기능 단위로 분리하는 것이 중요하다.

---

## **8) 시험 핵심 포인트**

- 유스케이스는 사용자 목표 단위이다.

- 동사 + 목적어 형태로 작성한다.

- 내부 처리 로직은 포함하지 않는다.

- 독립적인 완료 상태를 가져야 한다.

---

## **핵심 정리**

- 유스케이스는 사용자 목표 중심 기능 단위

- 식별 기준은 "목표성", "독립성", "상호작용"

- 내부 구현 로직은 제외

- 적절한 수준으로 분해하는 것이 중요

---

# **8. 액터와 유스케이스의 관계 (Association)**

---

## **1) 액터와 유스케이스 관계의 개념**

액터와 유스케이스의 관계는

**시스템 외부의 주체(액터)가 특정 기능(유스케이스)에 참여함을 나타내는 연결 관계**이다.

즉,

액터 ↔ 유스케이스

= "누가 어떤 기능을 사용하는가"를 표현한 것이다.

---

## **2) 표현 방식**

- 실선(Line)으로 연결

- 방향 화살표는 일반적으로 생략

- 의미: 상호작용(Communication)

유스케이스 다이어그램에서

가장 기본이 되는 관계이다.

---

## **3) 관계의 의미**

액터와 유스케이스가 연결되었다는 것은 다음을 의미한다.

- 액터가 해당 기능을 사용한다.

- 액터가 해당 기능을 시작할 수 있다.

- 시스템이 해당 기능 수행 시 액터와 상호작용한다.

---

## **4) 예시**

### **예시 1: 로그인 기능**

- 액터: 사용자

- 유스케이스: 로그인

→ 사용자 — 로그인

의미: 사용자는 로그인 기능을 수행한다.

---

---

## **5) 하나의 액터가 여러 유스케이스와 연결 가능**

예:

사용자

- 로그인

- 회원 가입

- 상품 검색

- 주문 생성

하나의 액터는 여러 기능을 수행할 수 있다.

---

## **6) 하나의 유스케이스에 여러 액터 연결 가능**

예:

유스케이스: 결제 처리

- 고객 (주 액터)

- 결제 시스템 (보조 액터)

하나의 기능에 여러 주체가 참여할 수 있다.

---

## **7) 주 액터와 보조 액터 관계**

### **주 액터**

- 유스케이스를 시작하는 주체

### **보조 액터**

- 시스템의 요청에 응답하는 외부 요소

예:

- 고객 → 결제 요청 (주 액터)

- PG 시스템 → 결제 승인 응답 (보조 액터)

---

## **8) 자주 발생하는 오류**

1. 내부 시스템 모듈과 연결

	- DB 서버 → 내부라면 연결 대상 아님

2. 모든 유스케이스를 모든 액터와 연결

	- 역할 구분이 필요

3. 액터 간 직접 연결

	- 액터는 서로 연결하지 않는다.

---

## **9) 시험 핵심 포인트**

- 액터와 유스케이스는 실선으로 연결

- 액터는 시스템 경계 밖

- 유스케이스는 시스템 경계 안

- 하나의 액터는 여러 유스케이스와 연결 가능

- 하나의 유스케이스에 여러 액터 참여 가능

---

## **핵심 정리**

- 액터와 유스케이스 관계는 상호작용 표현

- 가장 기본적인 유스케이스 다이어그램 요소

- 역할 기반으로 연결해야 함

- 내부 요소는 연결 대상이 아님
